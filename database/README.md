# 数据库部署与回归验证

权威 SQL 为 `migrations/2026090801_comments.sql`。它同时支持空库和本仓库旧版数据库，使用显式事务、迁移锁和 `app_private.migrations` 版本记录。

- 空库：在 Supabase SQL 编辑器以数据库所有者执行根目录 `supabase-setup-complete.sql`。
- 旧库：备份后，在测试项目演练，再以数据库所有者执行根目录 `supabase-migration-upgrade.sql`。
- 两个根目录文件是同一源文件的副本，修改权威 SQL 后运行 `npm run db:sync`；`npm run db:check` 防止副本分歧。
- 迁移会短暂阻止评论、点赞和注册的并发写入，应在维护窗口执行。任一步骤失败都会回滚整个事务；同一 SQL 编辑器连接若仍处于失败事务，先执行 `ROLLBACK` 后重试。

资料优先级：已经存在的 `profiles` 非空资料保留，空字段从旧 `astrohqy20250414` 表补全；缺失的 profile 优先采用旧表资料，再回退到认证元数据。用户名冲突自动追加完整用户 ID 与重试序号。旧资料表保留，便于核查；若此前迁移已生成非空默认资料，执行前应对照两表处理这类冲突，脚本不会盲目覆盖新表中可能由用户更新的值。一次性补全受版本记录保护，重跑不会恢复用户后来删除的简介。

楼层修复保留已有合法楼层，只将空值、非正数和重复项分配到最大楼层/持久计数器之后。清理已知保护及计数触发器在校准之前完成；结束前验证无重号、点赞计数正确。保留旧表中已经存在的历史正文，但匿名角色不能读取；作者只能读取自己的编辑历史。点赞表仅允许登录用户读取自己的点赞关系，公开计数仍来自 `comments.likes_count`。

`legacy/*.sql.disabled` 只用于旧库回归夹具及历史查阅。原根目录旧入口现在会主动抛错，不再执行建表、创建策略或覆盖触发器。

## 本地验证

```sh
npm ci
npm run verify
```

数据库测试使用内存 PGlite，模拟 `auth.users`、`auth.uid()`、`anon` 和 `authenticated`；应用权限测试使用普通角色，只有迁移以所有者执行。测试仅去掉 PGlite 不需要的扩展安装语句，保留实际迁移 SQL。它不代替托管 Supabase 的 PostgREST 嵌套查询、真实多连接并发和邮件恢复验收。

真实测试项目至少验收：旧资料与评论数量保持、用户名唯一、楼层唯一且不倒退、点赞计数与记录一致；两个账号分别注册/登录、编辑/取消点赞，匿名读取不能取得 IP、历史正文或点赞关系。数据库迁移通过后再部署对应前端。
